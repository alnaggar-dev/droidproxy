---
name: upstream-port
description: Integrate upstream commit-by-commit onto custom/main with ./.fork/port.sh, porting each upstream commit while preserving fork changes — no merge.
---

You are working on a personal fork that integrates upstream **commit by commit**, never by merging. Follow the Fork Maintenance section of your agent memory (CLAUDE.md or AGENTS.md), Porting from upstream. The driver `./.fork/port.sh` enforces the mechanics; your job is understanding each upstream change and re-applying it so your customizations survive.

Refuse to start if the working tree is dirty (port.sh refuses too).

Why a pointer, not a merge: there is no merge ancestry to say how far upstream you are, so `.fork/UPSTREAM` records the last ported upstream SHA. `port.sh` advances it in the *same* commit as each port and writes a `Fork-Flow-Port: <sha>` trailer — that trailer (not the staged file) is what the integration gate and `audit.sh` use to recognize a port, so a stray `git add` of the pointer can never masquerade as one.

Setup:
- Switch to custom/main, pull with --ff-only, fetch upstream (`git fetch --no-tags upstream`).
- On a fresh clone, wire the per-clone config first: `./.fork/setup.sh` (`--check` to inspect). Unwired, the hooks are silently off — port.sh still gates its own commits inline, but manual commits/merges are ungated. setup.sh CHAINS any hook manager the project already uses (husky, lefthook, real `.git/hooks` files — including a DORMANT `.husky/` dir on a clone that has not installed dependencies yet): the gate runs first, then the project's own hooks. Some managers re-point `core.hooksPath` on every dependency install (husky's `prepare` script) — `verify.sh` (full) and port.sh warn when that un-wires the kit; re-run `./.fork/setup.sh`.
- **Chained project hooks can REWRITE port commits.** A pre-commit formatter (`eslint --fix` + `git add`, `rubocop -a`) silently rewrites every port that touches its file types, so ported commits stop matching upstream (noisier future conflicts, degraded patch-id hints). port.sh sets `FORK_FLOW_PORT=1` in the environment of every port/unport commit and WARNS after any commit a hook rewrote — when you see that warning, tell the user, and propose guarding the project's hook (`[ -n "$FORK_FLOW_PORT" ] && exit 0` at the top, or the manager's skip mechanism). Do not silently keep porting through a rewriting hook.
- Confirm the driver isn't stale: if a fork-flow kit checkout is handy, `bash <kit>/install.sh --check` (it compares `.fork/VERSION`). On drift, `install.sh --update` before porting — otherwise you may be reasoning against an older `.fork/*.sh` than you think.
- If `.fork/UPSTREAM` is empty (a fork that has never ported), agree a starting point with the user — the upstream commit your fork last corresponded to — and initialize it: `./.fork/port.sh init <sha> [upstream-ref]`. This commits a one-time pointer-init (no code ported).
- See the backlog: `./.fork/port.sh list` (oldest-first, the order ports apply). The user may name a target ref/tag to stop at.

Port loop — repeat until the backlog is empty:
- `./.fork/port.sh next` ports the OLDEST unported commit (or `./.fork/port.sh one <sha>` to name that same oldest commit explicitly — it REFUSES an out-of-order SHA, since the pointer is contiguous; to grab one upstream commit early without advancing the pointer, cherry-pick it as a `custom:` change instead). It runs `git cherry-pick -x --no-commit`, and:
  - **Clean apply:** it stages the pointer, writes the trailer, and commits — the pre-commit gate runs `verify.sh --registry` automatically. Done.
  - **Conflict:** it STOPS, lists the conflicted files, and leaves you a paused port. Inspect with `./.fork/conflict-context.sh <sha> <file>` (pass the SHA it printed — it shows exactly what the upstream commit does to the file plus your recent local history). Re-apply the customization onto upstream's new code — never silently take upstream and drop the custom behavior. `git add` each resolved file, then `./.fork/port.sh continue`. To bail out: `./.fork/port.sh abort` (restores the tree).
- **Lockfile conflict** (`package-lock.json`, `pnpm-lock.yaml`, `bun.lock`, `Cargo.lock`, `poetry.lock`, …): never hand-merge one. Take upstream's side (`git checkout --theirs -- <lockfile>`), re-run the project's install so YOUR dependencies re-resolve on top (`npm install` / `pnpm install` / `cargo check` — whatever regenerates that file), then `git add` it and continue. The full `verify.sh` after the run proves the result; a hand-merged lockfile only ever *looks* right.
- **rerere replays past resolutions — including bad ones.** A conflict resolved once (by you or a previous agent run) is re-resolved the same way without passing your eyes: the file lands in the worktree with NO conflict markers, deliberately left unmerged (ports force `rerere.autoUpdate` off), and the pause banner lists it under **rerere AUTO-RESOLVED**. Treat each listed path as an unreviewed proposal, not a resolution: check it against what upstream changed (`git diff -- <file>`, `./.fork/conflict-context.sh <sha> <file>`) before you `git add` it. Wrong or stale? `git rerere forget <file>`, then `git checkout -m -- <file>` to restore the markers and resolve fresh — committing the fix re-records the right resolution. NEVER bulk-`git add` past that banner; that is exactly how a wrong fix re-commits itself forever.
- Understand BEFORE resolving: read the upstream commit (`git show <sha>`) and why it changed. `./.fork/brief.sh <sha>^ <sha>` flags which `.fork/CHANGES.md` entries its files touch (rename-, delete-, glob-aware). It also WARNS about unregistered fork changes — files no entry anchors, invisible to the briefing and the gate alike; register them with fork-change (or delete them) instead of porting blind over them.
- For a **structural or behavioral** change (not a trivial textual conflict), the one-line commit message rarely explains *why* — read the upstream **PR and any linked issue** before re-applying. Locate it from the `(#N)` in the commit subject or `gh pr list --search <sha>` (derive owner/repo from `git remote get-url upstream`), then read its description and review discussion (`gh pr view <N> --comments`, or open the PR URL with your reader). Adapt your customization to upstream's *new* design — match the new structure and behavior; don't force the old shape back onto it.
- A **direct-push** upstream commit has no PR — `gh pr list --search <sha>` returns nothing; fall back to the commit body and the diff for intent.
- Respect fork behavior even with NO conflict: the most dangerous port applies cleanly yet changes a function your fork depends on. Drift-check every touched entry with Symbols/Drift-if (LSP definition/hover when the symbol moved or the file is large) and record a short verdict.
- Update `.fork/CHANGES.md` (touched files, Symbols, Drift-if, Verify) if this commit changed a customization. Stage it before `continue` so it lands in the port commit.
- **Merge commits are ported automatically, as a unit — do NOT hand-cherry-pick them or build your own loop.** `port.sh next` walks upstream's first-parent line; when the next commit is a merge it replays the merge's first-parent diff (`cherry-pick -m 1`, still a cherry-pick — never a `git merge`), which carries every farm/second-parent commit the merge brought in *and* any evil-merge resolution that lives in no single commit. Inspect a merge's real content with `git diff <merge>^1 <merge>`; a plain `git show <merge>` is a combined diff that hides single-parent farm changes.
- The driver still refuses any move that would **rewind/sidestep** the pointer (ports must go forward). An **empty** cherry-pick (upstream change already present in your fork) still advances the pointer — the backlog shrinks honestly.

After the run — BEFORE you push:
- **Behavior-verify the run, not just the registry.** The registry gate that ran per commit is a *presence* check (most Verifies are greps and micro-asserts — they catch a dropped customization, not a broken behavior). Before pushing, run `./.fork/verify.sh` (full: install + lint + test + build, plus the merge=ours backstop and every entry's Verify). On a project where the full gate cannot realistically run (a monolith needing a provisioned DB, an install that takes tens of minutes), do NOT just skip it: run the project's OWN targeted test commands for **each registry entry whose files this run touched** (its test file, the suite for that module — derive from the entry's `Touches` paths) and say in your report which entries were behavior-tested and which ride on the registry gate alone.
- `./.fork/audit.sh`: confirm the **pointer consistency** section is clean (pointer is an ancestor of upstream, no retarget warning, the newest port trailer matches the pointer, no non-port commit edited the pointer), the backlog shrank, and review the **possibly reimplemented** (patch-id) section for customizations upstream now ships (mark `Status: superseded`, then retire them with the **drop-change** skill — retire BEFORE porting the upstream commit that ships the same change, so it ports clean). Register any UNREGISTERED files with the fork-change skill, or delete them (paths audit lists as *historical only* need nothing — they are gone everywhere).
- Review audit's **merge=ours divergence** section: it shows what each pin currently hides vs the ported upstream. For each pin, name WHY the divergence is intended (e.g. "upstream's new flags deliberately not adopted") — a pin you cannot explain is a drop candidate.
- Journal the run in `.fork/PORTS.md`. port.sh already appended a skeleton entry (with the conflict file list) for every conflicted port, range, and conflicted revert — replace its `(fill in)` lines with the real resolutions, drift verdicts, merge=ours decisions, and registry updates, and add the verify result. Batch a run of trivial clean ports into one entry.
- Push custom/main. The shipped CI workflow (`.github/workflows/fork-flow-gate.yml`) re-runs the registry gate server-side on the push — treat a red run as a failed port; it catches what a bypassed (`--no-verify`) or unwired local gate missed.

Edge cases:
- **Retargeting / upstream force-push:** porting from a different upstream branch/tag than recorded: pass the ref to `port.sh`/`audit.sh`; audit warns when the recorded ref differs. If the recorded pointer no longer sits on the line you port from (upstream force-pushed its history, or you switch to a rebased release branch), every port refuses — the pointer is forward-only. The sanctioned reset is `./.fork/port.sh init --force <sha> [ref]`, ONLY with the user's explicit agreement: pick the new-line commit your tree actually corresponds to (often `git merge-base HEAD <new-ref>`), re-initialize, then port forward. The forced re-init commits a fresh `Fork-Flow-Port-Init` trailer that audit treats as a sequence reset. NEVER hand-edit `.fork/UPSTREAM` instead — audit flags that as tamper permanently.
- **Reverting a port:** `./.fork/port.sh revert [<sha>]` un-ports the NEWEST port — it `git revert`s that port commit (which rewinds `.fork/UPSTREAM` automatically), records a `Fork-Flow-Unport: <sha>` trailer, and runs the gate (undoing a port must not silently break a customization either). On conflict it pauses like a port: resolve, `git add`, then `./.fork/port.sh continue` (or `abort`). Revert in reverse order — newest first; the driver refuses an older SHA. Re-port later with `./.fork/port.sh next`. A bare `git revert` also rewinds the pointer but is UNGATED and leaves audit warnings, so prefer the subcommand.
- **Rejecting an upstream change** (telemetry you refuse, behavior you keep different): you cannot skip a commit — the pointer is contiguous. Port it normally, then immediately land a registered counter-customization: one `custom:` commit reverting exactly that behavior, with a CHANGES.md entry (Reason: "intentionally drops upstream X"; a Verify proving the behavior stays gone — future ports will re-conflict here, and the entry is what protects your side). The fork-change skill registers it from the diff. NEVER hand-edit the pointer past a commit (audit flags that as tamper).
- **Large catch-ups — behind by one or more release tags:** switch from per-commit to per-release. `git fetch --tags upstream`, then `./.fork/port.sh range <oldest-unported-release-tag>` squash-ports the whole span pointer..tag as ONE gated commit: one conflict set per file (a hot file conflicts once per release instead of once per upstream touch) and one gate run per range instead of per commit. Read the release's changelog/notes for intent instead of per-commit messages; on conflict inspect with `./.fork/conflict-context.sh <from>..<to> <file>` (port.sh prints the exact command). Months of drift usually include upstream DELETING a file the fork modified (and the mirrors: you deleted what they modified, both added the same path) — `range` stages each of those as a conflict that pauses like any other: decide per file with `git rm <file>` (accept their deletion / yours) or `git add <file>` (keep yours / adapt theirs), and find the deleted feature's new home before discarding your change onto a dead file. Repeat tag-by-tag, oldest first, until you are inside the current release cycle — then return to `./.fork/port.sh next`. A bad range is one `./.fork/port.sh revert` away (the pointer rewinds to the span's start). Within per-commit runs the registry gate is cheap — do NOT reach for `FORK_SKIP_VERIFY` to "speed up" a run, and do NOT batch many ports behind one late verify. Ports are strictly SEQUENTIAL — one pointer, one working tree — so NEVER run two ports (or a port plus any other tree-mutating work) in parallel; subagents may take only read-only work (analyzing independent risky commits, reading PRs/changelogs, drafting a resolution) while every `port.sh` command and every resolve-and-commit stays in the main thread, one port at a time, with no project-wide verification inside subagents.
- **Submodules are out of scope:** a port carries submodule pointer bumps like any other change, but the registry/gate has no notion of what is inside them — verify a submodule-touching port by hand.

Report: the pointer's old and new SHA, commits ported (with upstream SHAs), conflicts resolved, drift verdicts, merge=ours decisions, CHANGES.md updates, audit findings (consistency + reimplemented), the PORTS.md entries, and verification results.
